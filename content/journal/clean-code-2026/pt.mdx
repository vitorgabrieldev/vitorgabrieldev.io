## O Problema: Clean Code Virou Dogma

Clean Code de 2008 (Uncle Bob) era necessário:
• Nomes descritivos (vs `a`, `x`, `temp`)
• Funções pequenas (vs 500-line methods)
• Sem comentários (vs explicar código ruim)
• Single Responsibility (vs fazer 10 coisas)

**Verdade da época:** Humanos leem código 10x mais que escrevem. Legibilidade era o gargalo.

**Verdade de 2026:** IA lê seu código e te avisa quando tá ruim. Copilot, ChatGPT, Cursor — você não tá só legível pra humanos, tá legível pra máquinas.

## O Que Mudou

### 1. Código Ruim Não Passa Despercebido

Antes (2008):
```php
// Sem IA, isso passa (humano cansado não vê)
function process($d) { // Param `$d` é vago
  $r = [];
  foreach ($d as $v) {
    if ($v['s'] == 'ok') { // Magic string 's'
      $r[] = $v['p']; // What is 'p'?
    }
  }
  return $r;
}
```

Agora (2026):
```php
// Cursor/Copilot avisa imediatamente
function process($data) { // WARN: Ambiguous variable name
  $result = [];
  foreach ($data as $item) {
    if ($item['status'] == 'ok') { // LINT: Use constant
      $result[] = $item['price']; // SUGGEST: Extract to method
    }
  }
  return $result;
}
```

**Conclusão:** Você não precisa que seu código seja "bonito pra humanos lerem". Precisa que seja **explicável em auditoria**.

### 2. Observabilidade Substitui Legibilidade

Antes era:
"Se o código é limpo, você entende o que tá acontecendo"

Agora é:
"Se o código tá rodando em produção, você precisa ver:
• Qual função rodou
• Com quais inputs
• Quanto tempo levou
• Qual decisão tomou
• Por que falhou"

```php
// ❌ ERRADO: Legível mas sem trace
public function transfer($from, $to, $amount)
{
  if ($from->balance < $amount) {
    return false; // Falhou, mas por quê?
  }
  
  $from->balance -= $amount;
  $to->balance += $amount;
  
  return true;
}

// ✅ CORRETO: Observável
public function transfer($from, $to, $amount)
{
  Log::info('Transfer initiated', [
    'from_id' => $from->id,
    'to_id' => $to->id,
    'amount' => $amount,
  ]);
  
  if ($from->balance < $amount) {
    Log::warning('Transfer failed: insufficient balance', [
      'from_id' => $from->id,
      'required' => $amount,
      'balance' => $from->balance,
      'shortfall' => $amount - $from->balance,
    ]);
    return false; // Agora você SABEporquê falhou
  }
  
  $from->balance -= $amount;
  $to->balance += $amount;
  $from->save();
  $to->save();
  
  Log::info('Transfer completed', [
    'from_balance' => $from->balance,
    'to_balance' => $to->balance,
  ]);
  
  return true;
}
```

### 3. Rastreabilidade > Pureza Arquitetural

Antes:
"Seu código precisa respeitar Clean Code principles"

Agora:
"Se você não consegue rastrear uma decisão até a pessoa/ticket que pediu, o código tá incompleto"

```php
// ❌ ERRADO: Decision misterioso
if ($user->created_at->diffInDays() > 30) {
  $discount = 0.1; // Por que 10%? Quem pediu?
}

// ✅ CORRETO: Rastreável
// TICKET-4521: Loyalty discount for 30+ day users
// @requester: Product team
// @date: 2026-03-15
if ($user->created_at->diffInDays() > 30) {
  $discount = 0.1; // Loyalty program tier
  
  Log::info('Loyalty discount applied', [
    'user_id' => $user->id,
    'discount_percent' => $discount * 100,
    'ticket' => 'TICKET-4521',
  ]);
}
```

## Novo Foco: Auditabilidade

### O Que Significa Auditável?

**Sua função auditável é quando:**

1. **Input is logged**
```php
public function processOrder(Order $order)
{
  Log::info('Order processing start', [
    'order_id' => $order->id,
    'items_count' => $order->items->count(),
    'total' => $order->total,
  ]);
  // ...
}
```

2. **Decisions are logged with reason**
```php
if ($order->total > 1000) {
  // DECISION: High-value order, require approval
  $order->status = 'pending_approval';
  Log::info('Order flagged for approval', ['reason' => 'high_value']);
} else {
  $order->status = 'processing';
  Log::info('Order auto-approved', ['reason' => 'below_threshold']);
}
```

3. **Failures are specific**
```php
try {
  $payment = Stripe::charge($order->total);
} catch (StripeException $e) {
  Log::error('Payment failed', [
    'error_code' => $e->getCode(),
    'message' => $e->getMessage(),
    'order_id' => $order->id,
    'timestamp' => now(),
  ]);
  // DON'T just return false
  throw $e; // Rastreável no APM
}
```

4. **Output is logged**
```php
public function processOrder(Order $order)
{
  // ... process ...
  
  Log::info('Order processed', [
    'order_id' => $order->id,
    'new_status' => $order->status,
    'items_processed' => $processed_count,
    'duration_ms' => now()->diffInMilliseconds($start_time),
  ]);
  
  return $order;
}
```

## Checklist: Code é Auditável?

**SIM a:**
• Cada decisão tem log de por que foi tomada
• Falhas têm erro code específico + contexto
• Chamadas externas (API, DB) são rastreadas
• Inputs/outputs relevantes estão logados
• Tempo de execução é monitorado
• Mudanças de estado têm trail

**NÃO:**
• Só porque é legível pra humano
• Só porque segue Clean Code principles
• Só porque o código é "bonito"
• Se não tem observability

## Exemplo: Auditável vs Bonito

```php
// ✅ AUDITÁVEL (não é o mais "clean")
public function updateUserStatus(User $user, string $newStatus)
{
  $oldStatus = $user->status;
  
  Log::info('User status update initiated', [
    'user_id' => $user->id,
    'from' => $oldStatus,
    'to' => $newStatus,
    'triggered_by' => auth()->id(),
  ]);
  
  // Validação com logging
  $validTransitions = [
    'active' => ['suspended', 'inactive'],
    'suspended' => ['active', 'inactive'],
    'inactive' => ['active'],
  ];
  
  if (!in_array($newStatus, $validTransitions[$oldStatus] ?? [])) {
    Log::warning('Invalid status transition', [
      'user_id' => $user->id,
      'from' => $oldStatus,
      'to' => $newStatus,
      'allowed_transitions' => $validTransitions[$oldStatus] ?? [],
    ]);
    throw new InvalidStatusTransitionException();
  }
  
  $user->status = $newStatus;
  $user->save();
  
  Log::info('User status updated', [
    'user_id' => $user->id,
    'new_status' => $user->status,
    'timestamp' => now(),
  ]);
  
  event(new UserStatusChanged($user, $oldStatus));
}
```

Compara com esse "Clean Code puro":

```php
// ❌ BONITO MAS NÃO AUDITÁVEL
public function updateUserStatus(User $user, string $newStatus)
{
  if (!$this->isValidTransition($user->status, $newStatus)) {
    throw new InvalidStatusTransitionException();
  }
  
  $user->status = $newStatus;
  $user->save();
  event(new UserStatusChanged($user));
}

private function isValidTransition(string $from, string $to): bool
{
  return in_array($to, $this->allowedTransitions[$from] ?? []);
}
```

O segundo é mais "clean", mas:
• Não sabe quem pediu mudança
• Não loga decisão (why?)
• Não diferencia erro (qual transição inválida?)
• Impossível auditar em produção

## Clean Code em 2026: O Novo Contrato

**De:**
• Nomes bonitos
• Funções pequenas
• Sem comentários

**Para:**
• Nomes rastreáveis (IDs, contexto)
• Funções com logging de decisão
• Documentação de decisão (ticket, requester, date)

## Resumo

**Clean Code 2008 = Legibilidade**
**Clean Code 2026 = Auditabilidade + Observabilidade + Rastreabilidade**

Seu código não precisa ser o mais bonito.
Precisa deixar pistas de por que fez cada coisa.
